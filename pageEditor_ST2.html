Splash Screen

Technical Description

HTML Technical Description

  • A <section class="hero"> element was used as the outermost wrapper, containing all visual layers including the background image, moon, ripples, and content panel.
  • The background image was implemented as an <img> element positioned absolutely with object-fit: cover, ensuring proportional scaling across all screen sizes.
  • A CSS overlay was applied using the ::after pseudo-element with a linear-gradient, darkening the image edges to improve text readability.
  • The moon and halo were placed as separate absolutely positioned elements, initially given negative top values to keep them off-screen on load.
  • The hero content panel used backdrop-filter: blur(28px) to produce a frosted-glass effect over the background.
  • The automatic redirect was implemented using <meta http-equiv="refresh" content="6;url=home.html"> placed in the <head>, as specified in the coursework requirements.
  • Bioluminescent dots and ripple rings were generated dynamically — a for loop creates each element, assigns randomised CSS custom properties inline, and appends them to their containers.
  • A <div class="loader-wrap"> was included inside the hero content panel containing a CSS-only loader ring animation and a countdown <p> element, visually reinforcing the transition period before redirect.
  • A <div class="moonReflection"> element was placed at the bottom of the hero section to simulate the moon's reflection on the water surface, fading in separately from the moon itself via a delayed CSS transition
  • A <div id="stars"> container was used to hold the dynamically generated bioluminescent dots, keeping generated content separated from static markup

CSS Technical Description

  • The .loaded class is added via JavaScript after a 300ms delay, triggering CSS transition with cubic-bezier(0.22, 1, 0.36, 1) easing to produce the moon rising effect.
  • clamp() was used throughout for font sizes and spacing, allowing fluid scaling between screen widths without breakpoint-specific media queries.
  • Animations for dots and ripples are handled entirely in CSS using @keyframes, keeping behaviour and presentation separated.
  • z-index layering was used to stack all visual elements correctly — background at z-index 1, overlays at 2, moon at 6, content panel at 10.
  • The loader ring was implemented using a rotating <div class="loader-ring"> with a <div class="loader-dot"> child — both animated purely in CSS using @keyframes, with no JavaScript involvement.
  • CSS custom properties such as --bio, --deep, --glow, and --radius-sm were used throughout, referencing values defined in the global style.css, ensuring visual consistency with the rest of the website.
  • The moon reflection used transition: opacity 1.8s ease 0.8s — the 0.8s delay was intentional, causing the reflection to appear slightly after the moon itself for a more natural visual sequence.
  • The bioTwinkle and rippleOut animations both use randomised --duration and --delay custom properties set inline by JavaScript, allowing each dot and ripple to animate independently without separate CSS rules for each element.

JavaScript Technical Description

  • The window.addEventListener('load', ...) pattern ensures everything waits for the full page load before animations trigger.
  • The var(--bio) and other CSS custom properties are used across multiple elements for consistent styling and animation timing.
  • The moon reflection element (moonReflection) has a separate fade-in transition, creating a more natural visual sequence after the moon itself appears.
  • The loader ring and loader dot are CSS-only animated elements inside the content panel, with no JavaScript involvement for animation.
  • The skipIntro() function removes the meta tag using document.querySelector('meta[http-equiv="refresh"]').remove(), preventing the automatic redirect if desired.
  • The stars container is reused for the dynamically generated bioluminescent dots, with id="stars" feeding multiple animations.

Accessibility

  • All image elements were given descriptive alt attributes — the hero background uses alt="Night ocean scene with clouds and stars" and the moon uses alt="Full moon rising over the ocean".
  • The skip button is implemented as a native <button> element, making it keyboard-focusable and correctly announced by screen readers without additional ARIA roles.
  • The lang="en" attribute is set on the <html> element, allowing screen readers to apply the correct language profile.
  • A single <h1> is used for the page title, maintaining a correct and logical document outline.
  • Text colours were chosen to maintain sufficient contrast against the dark background — for example, the main heading uses near-white #eef6fa over a semi-transparent dark panel.
  • The countdown and skip button both carry clear visible text labels, making the transition behaviour understandable to all users.

AIS Page

Technical Description

HTML Technical Description

  • The page was structured using a <main> element containing a hero introduction section followed by the simulator panel.
  • Six action cards were marked up as <div> elements, each containing a thumbnail <img> with descriptive alt text, a category <span> label, an <h2> card title, a <p> description, and an impact point <span>.
  • Each card was given role="checkbox" and aria-checked="false" as default attributes for accessibility.
  • The simulator feedback container was marked up with role="region" and styled with backdrop-filter: blur(18px).
  • A fixed-position <img id="sceneBg"> element was used as the dynamic background, layered behind all content via z-index.
  • The action card grid container was marked up with role="group" to semantically group the interactive cards.
  • The reset button was implemented as a native <button> element, ensuring keyboard accessibility without additional ARIA roles.
  • A <footer> was included containing links to the Page Editor, Validation Page, Accessibility, and Compliance sections.

CSS Technical Description

  • Three impact level classes were defined: impact-low, impact-mid, impact-high, each changing border colour, box shadow, and text colour when applied.
  • All colour transitions were handled using transition: all 0.7s ease, keeping visual changes separated from JavaScript logic.
  • The action card grid was laid out using display: grid with grid-template-columns: repeat(3, 1fr), with responsive breakpoints at 900px (2 columns) and 520px (1 column) using @media queries.
  • A scorePop animation was defined using @keyframes and triggered via JavaScript class toggling, producing a bounce effect whenever the score changes.
  • A cardEntry animation was applied to each card using animation-delay on :nth-child selectors, staggering the cards as they load in.
  • A ptsFloat animation was defined for the floating toast notifications, fading and translating upward over 1 second.
  • A rippleAnimation @keyframes was defined to scale a circular element outward and fade it to opacity 0, producing the water ripple effect on card click.
  • The progress bar fill used transition: width 0.7s cubic-bezier(0.22, 1, 0.36, 1) for smooth animation and a linear-gradient spanning red through amber to green.
  • The selected CSS class visually distinguishes selected cards through border colour and background change.
  • The .card:hover style changes border colour and box shadow on hover, providing clear visual feedback that the cards are interactive.
  • The tick indicator inside each card uses opacity: 0 by default and opacity: 1 when the selected class is applied, visually confirming selection without relying on colour alone.

JavaScript Technical Description

  • A cardData object was defined to store the point value assigned to each card using card IDs as keys — e.g. card 1 carries 3 points, card 2 carries 4 points.
  • A selected object was used to track the selection state of each card, storing boolean values against each card ID.
  • A currentBg variable was used to track the currently displayed background image, preventing unnecessary DOM updates when the level has not changed.
  • A prevLevel variable was used to track the previous impact level, allowing the code to detect level changes and trigger animations only when the level actually shifts.
  • A messages object was defined containing feedback data for each impact level — including badge label, feedback message, ocean description text, and emoji icon.
  • A backgrounds object was defined mapping each impact level to its corresponding background image file path.
  • calcScore() iterates through the selected object using a for...in loop, summing point values from cardData for every card marked as true, and returns the total.
  • countSelected() uses Object.values(selected).filter(Boolean).length to count and return the number of currently selected cards.
  • toggle(id, e) is the main card interaction handler, retrieving the card element by ID, calling spawnRipple(), determining selection or deselection, toggling the selected state and CSS class, calling spawnToast(), and then calling updateFeedback().
  • spawnRipple(card, e) calculates the click position relative to the card using getBoundingClientRect() and event.clientX / clientY, creates a <span> element sized 1.2× the card's largest dimension, positions it at the click coordinates, appends it to the card, and removes it after 600ms via setTimeout().
  • spawnToast(pts, adding, cardEl) creates a <div> positioned near the clicked card using getBoundingClientRect(), sets text to +pts or −pts depending on selection, adds a neg class for deselection to apply red colouring, appends it to <body>, and removes it after 1000ms via setTimeout().
  • updateFeedback() is the central update function called after every interaction and performs the following sequence:
    • calculates current score and selected count;
    • determines impact level based on thresholds — 0 = none, 1–5 = low, 6–11 = mid, 12+ = high;
    • updates the score display and applies the correct colour class, triggering the pop animation via forced reflow void scoreEl.offsetWidth;
    • updates the progress bar width as a percentage of 17 points;
    • updates the impact level badge text and class, triggering a pulse animation only when the level changes;
    • fades feedback message out using opacity: 0, updates text after 220ms, and fades back in only when level changes;
    • updates selected actions counter, ocean icon, and description text;
    • updates CSS classes on ocean state box and feedback panel;
    • checks whether background image needs to change, if different, fades <img> to opacity: 0, updates src after 500ms, then fades back to opacity: 1.
  • resetall() iterates through all card IDs in cardData, sets each selected entry to false, removes the selected CSS class from each card, and calls updateFeedback() to return everything to default.
  • updateFeedback() is also called once on page load to initialise all display elements to their default values without requiring user interaction.

Accessibility

  • Each action card was given role="checkbox" and an aria-checked attribute toggled between "true" and "false" via JavaScript, communicating selection state to assistive technologies.
  • All card images carry descriptive alt text relevant to their content — e.g. alt="Single use plastic bottles on a beach" and alt="Volunteers cleaning a beach".
  • The action card grid container was marked up with role="group" to semantically group the interactive cards together.
  • The reset button was implemented as a native <button> element to ensure full keyboard accessibility.
  • The back-to-top anchor link was given aria-label="Back to top" to provide a meaningful label beyond the arrow symbol used visually.
  • The dynamic background <img> carries a descriptive alt attribute explaining that it changes in response to the user's score.
  • Heading hierarchy was maintained with a single <h1> for the page title and <h2> elements used for card titles.

Content Page

Technical Description

  • The shared content page template was collaboratively created by Nethnu Bulathsinghala and Kulith Silva.
  • The technical description and accessibility are consistent and shared across the entire team.

HTML Technical Description

  • <!DOCTYPE html> and <html lang="en"> define the document as HTML5 and set the language for accessibility and correct interpretation.
  • <meta charset="UTF-8"> ensures support for a wide range of characters and symbols.
  • <meta name="viewport"> enables responsive design by matching the layout to the device width.
  • <link rel="stylesheet"> imports external CSS files and Google Fonts to style the page.
  • <header> and <nav> structure the navigation bar, improving usability and accessibility.
  • <main> wraps the primary content, helping screen readers identify the main section of the page.
  • <section> elements divide the page into logical content areas such as hero, content cards, and handoff.
  • id attributes (e.g., #top, #act3) are used for internal navigation and anchor linking.
  • class attributes are used to apply consistent styling and layout through CSS.
  • data-* attributes (e.g., data-bg, data-ch) store custom data used by JavaScript for dynamic behaviour.
  • <img> elements include alt text for accessibility and onerror to hide images if they fail to load.
  • aria-hidden="true" is used to hide decorative elements from screen readers.
  • <a> elements provide navigation between pages and within the page using anchor links.
  • <script src="..."> links an external JavaScript file, separating behaviour from structure.
  • <footer> contains additional navigation and student details, placed at the end of the page.

CSS Technical Description

  • body sets a dark background colour, creating the base theme of the page.
  • .sonar uses position: absolute, border-radius: 50%, and transform to create circular ripple elements.
  • @keyframes sonarRing defines the ripple animation using transform and opacity to simulate expanding waves.
  • .sonar.fire, .fire2, and .fire3 apply staggered animations using delays for a layered ripple effect.
  • #sonarpart uses position: fixed and pointer-events: none so the animation stays centred and does not block user interaction.
  • .bg uses position: fixed and opacity transitions to create smooth background image changes.
  • .bg.active switches visibility by increasing opacity and z-index, controlling which background is shown.
  • .bimg uses object-fit: cover to ensure images fill the screen without distortion.
  • .bg::after applies gradient overlays using pseudo-elements to improve text readability over images.
  • .chapters uses Flexbox (display: flex) to centre content both vertically and horizontally.
  • clamp() is used for responsive font sizes, adjusting text smoothly across different screen sizes.
  • .contentcon uses backdrop-filter: blur() and semi-transparent backgrounds to create a glassmorphism effect.
  • .contentcon.visible uses opacity and transform transitions to animate content appearing on scroll.
  • z-index is used throughout (e.g., background = 0, content = 10) to control layering of elements correctly.
  • @keyframes scrollDrop animates the scroll indicator line using transform and opacity for a looping effect.

JavaScript Technical Description

  • document.getElementById() is used to select specific elements such as the scroll bar and sonar rings.
  • document.querySelectorAll() selects multiple elements (e.g., sections with data-bg) and converts them into an array using Array.from().
  • reduce() is used to create an object mapping background IDs to their corresponding DOM elements for efficient access.
  • switchBg() function controls background transitions by adding and removing the active class.
  • classList.add() and classList.remove() dynamically update CSS classes to change styles and trigger animations.
  • setTimeout() is used to delay actions such as resetting z-index and controlling animation timing.
  • window.addEventListener('scroll') listens for scrolling to update the progress bar and trigger effects.
  • window.pageYOffset and document height calculations are used to determine scroll progress.
  • getBoundingClientRect() calculates the position of sections to detect which section is closest to the viewport centre.
  • dataset (e.g., dataset.bg) accesses custom HTML data attributes to control background switching.
  • IntersectionObserver detects when elements enter the viewport and adds a visible class for animations.
  • addEventListener('load') ensures initial functions run only after the page fully loads.

Accessibility

  • lang="en" defines the page language, helping screen readers use correct pronunciation.
  • alt attributes on images provide descriptions for visually impaired users.
  • aria-hidden="true" hides decorative elements (e.g., background images, sonar effects) from screen readers.
  • <header>, <nav>, <main>, <section>, and <footer> create a semantic structure for easier navigation.
  • aria-label (e.g., "Back to top") gives meaningful descriptions to icons or non-text elements.
  • <a> links enable keyboard navigation between sections and pages.
  • <em> and <strong> provide semantic emphasis, improving how screen readers interpret content.
  • id attributes allow users to jump to sections using anchor links, supporting keyboard navigation.

Challenges and Lessons Learned

  • Coordinating the countdown timer with the <meta http-equiv="refresh"> required careful timing. The meta tag fires after 6 seconds, but the visible countdown needed to start from 4, so a 2 second delay was introduced before the setInterval() began, with the initial counter value set to 6 to account for the hidden loading window. Getting these two mechanisms to stay in sync without the numbers appearing to jump took several adjustments.
  • Canceling the meta refresh when the skip button is pressed was not straightforward, as the <meta http-equiv="refresh"> tag cannot be paused once the page has loaded. The solution was to remove the element from the DOM entirely using document.querySelector('meta[http-equiv="refresh"]').remove() , which was a behaviour that required understanding how the browser processes meta elements at runtime rather than just how to write HTML attributes.
  • Sequencing the entrance animations — the moon rising, the halo fading in, the hero content appearing, and the info panel sliding up — required all elements to be revealed through separate CSS transitions with staggered delays, triggered simultaneously by adding a loaded class in JavaScript after a short timeout. Ensuring no element appeared before its parent container was ready took careful layering of transition-delay values, and the ordering only became clear after testing repeatedly in the browser.
  • The bioluminescent dots and ripple rings are generated entirely in JavaScript, with randomised size, opacity, position, duration, and delay values injected as inline CSS custom properties. Passing those custom properties through to the @keyframes animation rules, rather than hardcoding values, required understanding how CSS variables interact with animation declarations, which was not something covered directly in lectures and took independent research to get working correctly.
  • The global style.css applies padding-top: 50px to the body universally, which causes unwanted spacing on the splash screen since it does not use the shared header. Overriding this required explicitly setting padding-top: 0px !important in the splash-specific CSS, which was only discovered during integration testing when the shared stylesheet was first linked.
  • For the AIS page, implementing card toggling so that clicking a selected card would correctly deselect it and subtract its points from the running total required the JavaScript to check the card's current state before deciding whether to add or subtract, rather than simply accumulating points on every click. Getting the logic right for edge cases, such as rapidly clicking the same card, took more iteration than expected.
  • Triggering a background image change based on three distinct impact thresholds required defining clear point boundaries in the JavaScript and using those in a conditional block that updated the page background directly through the DOM. Ensuring the content remained readable at all three background levels required additional overlay adjustments for each impact state.
  • Keeping the embedded CSS in the AIS page scoped to that page without conflicting with the shared style.css rules required reviewing every selector carefully to avoid accidentally overriding navigation or card styles inherited from the global stylesheet. Coming from a background that was stronger in CSS than JavaScript, this separation of concerns was one of the more practically useful things the project reinforced.
  • Working across two technically different pages — a standalone animated splash screen and a JavaScript-driven interactive simulator within the same shared codebase made it clear how much careful planning of CSS scope and file structure matters in a group project. On the JavaScript side, moving from a purely CSS mindset to thinking about state, conditionals, and DOM manipulation required a shift in approach that became more natural over the course of the project. Testing each page both in isolation and with the shared stylesheet applied early on would have caught several integration issues sooner, and that is something to carry into future projects.

Compliance

  • All pages include a valid <!DOCTYPE html> declaration and lang attribute, ensuring properly structured HTML5 documents.
  • Both pages were validated using the W3C HTML Validator to check for structural errors, unclosed tags, and incorrect nesting.
  • CSS was validated using the W3C CSS Validator to confirm no invalid properties or syntax errors exist.
  • Images include alt attributes and interactive elements use semantic tags, meeting basic accessibility requirements.
  • All images are generated using Google Gemini and Google Fonts are loaded via their official API under open licence, ensuring no copyright violations.
  • External resources load over HTTPS, complying with secure resource loading requirements.
  • No personal data is stored beyond the current session, aligning with data minimisation principles.
  • Pages contain no offensive, discriminatory, or misleading content, complying with Janet's acceptable use standards.
  • Responsive design ensures pages are accessible across a range of devices and screen sizes.
